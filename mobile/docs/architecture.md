# Architecture

## Layering

```
app/            Expo Router screens — thin: layout + hooks + presentational JSX only
features/       Feature-first business logic: zod schemas, TanStack Query hooks
services/       Repository layer — the ONLY place that calls supabase.from(...)
lib/            Cross-cutting singletons (supabase client, query client, logger)
store/          Zustand: small, global, cross-feature UI/auth state
providers/      React context providers wired in app/_layout.tsx
components/ui/  Presentational, feature-agnostic primitives (Button, Card, ...)
types/          Generated DB types (types/database.ts) + ergonomic aliases (types/models.ts)
utils/          Pure functions with no I/O — the most heavily unit-tested layer
```

Data flows one direction: **screen → feature hook → service → Supabase**. A screen never
imports `lib/supabase` directly; a service never imports a React hook. This is what
makes `utils/slots.ts`, `utils/health.ts`, `utils/queue.ts`, and the zod schemas testable
without mocking the network (see their colocated `*.test.ts` files).

## Why Supabase types are generated, not hand-written

`types/database.ts` is produced by the Supabase MCP `generate_typescript_types` tool
against the live schema — it is regenerated after every migration, never edited by hand.
`types/models.ts` re-exports ergonomic aliases (`Doctor`, `Appointment`, ...) over it.

## Auth flow

`providers/AuthProvider.tsx` hydrates a Zustand store (`store/authStore.ts`) from
`supabase.auth.getSession()` on launch and keeps it in sync via
`onAuthStateChange`. `app/_layout.tsx` uses Expo Router's **protected routes**
(`Stack.Protected guard={...}`) to show either the `(auth)` stack or the `(tabs)` stack —
there is no manual `router.replace` redirect dance. `reset-password` is declared outside
both protected groups because it must be reachable from a password-reset email deep link
regardless of whether a session already exists.

Session persistence uses a custom `LargeSecureStore` (`storage/secureStore.ts`): Expo
SecureStore caps values at ~2048 bytes, too small for a Supabase session (JWT access +
refresh token + user object), so the session is AES-256 encrypted and stored in
AsyncStorage, with only the small encryption key kept in SecureStore. This is Supabase's
own documented pattern for Expo apps, not a custom invention.

## State management strategy

- **Server state** (anything from Supabase): TanStack Query, one hook per concern under
  `features/*/use*.ts`. Query keys are centralized in `constants/queryKeys.ts` so a
  fetch and its corresponding cache invalidation can't drift out of sync.
- **Realtime**: `services/notifications.service.ts` and `services/checkins.service.ts`
  open `postgres_changes` channels and invalidate the relevant query key on change,
  rather than maintaining a second, parallel copy of server state in Zustand.
- **Client/global state**: Zustand, kept deliberately small — just `authStore`
  (session, profile). Nothing else needed a global store; per-screen state is plain
  `useState`.

## Navigation

Expo Router, file-based:

- `(auth)` — login, signup, forgot-password (stack, no header)
- `(tabs)` — Home, Departments, Doctors, Appointments, Profile (bottom tabs)
- `doctor/[id]`, `booking/[doctorId]`, `notifications`, `scan` — pushed/modal screens
  outside the tab bar, reachable from the tabs

The booking flow is intentionally a **single screen** (`booking/[doctorId].tsx`) with
local step state (date → slot → reason), not four separate routes — the spec's
Hospital → Department → Doctor steps ARE separate screens (Departments tab → Doctors
tab, filtered → doctor profile), but date/slot/reason are one continuous decision for
the user and splitting them into more navigation stack entries would only add
back-button friction.

This deployment is scoped to a **single hospital** — there is no hospital picker
anywhere in the UI. `services/hospitals.service.ts` exposes one function,
`getPrimaryHospital()`, which every screen that needs the hospital's id (booking,
QR check-in) resolves through rather than a user selection. The `hospitals` table
itself still exists (one row) so `departments`/`doctors`/`appointments`/`checkins`
keep a normalized FK rather than a denormalized hospital name — if a second hospital
is ever needed, that's a UI change (reintroduce a picker), not a schema change.

## The QR spot check-in feature

The web app's existing kiosk (`src/pages/PatientCheckIn.jsx`) shows a QR that opens a
browser check-in page for an anonymous walk-in. The mobile app's `/scan` screen is the
authenticated, native evolution of the same idea: `expo-camera`'s built-in QR scanning
reads a **counter QR** (a static deep link `sportingethos://checkin`, generated by
`scripts/generate-counter-qr.mjs` — see [deployment-guide.md](deployment-guide.md)) and
creates a `checkins` row tied to the logged-in patient's `profile.id` (and the single
hospital, resolved via `getPrimaryHospital()`) in one tap, instead of free-typing a
name. See [database.md](database.md) for how this coexists with the existing
anonymous kiosk data.

## What's deliberately not built (and why the schema still supports it)

Doctor/admin portals, prescriptions, lab orders, medicine ordering, reports, insurance,
and telemedicine are out of scope for this pass (see the root plan / PR description for
the full reasoning — this is a hackathon demo, not a months-long enterprise build).
Every table added is 3NF-normalized with proper FKs specifically so these can be layered
on later as new tables (`prescriptions`, `lab_orders`, `medicine_orders`, ...) without
migrating or breaking anything that exists today.
